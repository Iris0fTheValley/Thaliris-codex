# Native two-region investigation harness

Use this outline for a real Native acceptance run after the candidate is installed in a
new isolated runtime. The owning Controller keeps the complete user objective, hard
invariants, acceptance criteria and final product judgment. This harness guides
observation; it does not establish model compliance by itself.

## Prompt template

> Investigate these independent source questions through two fresh registered
> Investigator roles. Region A: `[source pointers and one bounded question]`. Region B:
> `[source pointers and one bounded question]`. For each, return a concise conclusion,
> exact source references, verification performed, contradictions and decision-changing
> UNKNOWN. Do not edit source or production Host state. The owning Controller retains the
> complete product objective, acceptance and integration decision; use only the selected
> scope in your handoff and keep the private working set local.

Before each top-level managed dispatch, select its opaque requirement references,
logical candidate and exact role/profile through the existing `task-evidence-register`
operation's optional `next_dispatch` metadata. Register requirements in that same operation
or earlier. Let the Controller choose the applicable task mode and native bindings. Do not
pre-script an imagined dispatch/wait trace or coach a child toward a result.

## Run and evidence

1. Observe the actual two dispatches and the Hook-delivered handoff text. Verify the
   preselection was consumed once by each matching reservation and the exact task-local
   handoff association existed before Native execution. A readable marker in
   the request does not prove the Host delivered it in readable form.
2. After dispatch, finish only independent work that can change the next decision. When
   none remains and a direct child is unfinished, use the Host's supported meaningful
   wait. Do not repeat the delegated search, tests or diff review while waiting.
3. Preserve each child conclusion, exact source refs, verification and UNKNOWN separately.
   If a legacy unselected handoff appears in `unassociated_handoffs`, retain the explicit
   exact-ID registration recovery with normal revision CAS. Do not infer markers,
   candidate relevance or requirement refs from role or lineage.
4. Once results arrive, integrate them with the retained objective and invariants. If one
   immediate decision depends on an unresolved source fact, make one precise source
   spot-check and record which decision it resolves. Route repair or preserve UNKNOWN
   when evidence does not resolve the acceptance criterion.

Use an opaque Hook-delivered message and record the child's first inline observation
before the Controller acknowledges the spawn. It must succeed without postspawn
association or retry. For a separate nested Scanner scenario, preselect its top-level
parent before dispatch, then let the parent dispatch the Scanner before its own spawn
acknowledgement. Verify exact parent lineage, logical candidate, empty Scanner requirement
refs, the first stored observation and its reappearance in ordinary Controller context.
Postspawn association remains a legacy recovery and cannot establish race-free first
recording. A conflicting readable marker must refuse without consuming the selection.

For a Windows PowerShell `.cmd` runner, use literal backslashes before JSON double quotes
inside the single-quoted inline argument, for example
`--observation-json '{\"id\":\"O1\",\"text\":\"local fact\",\"source_refs\":[\"S1\"]}'`.
Include registered or inline source refs as usual. Unescaped PowerShell-to-batch JSON
can lose its quotes before the CLI; record that serialization boundary separately from
evidence-association behavior. This requires no payload file write or child retry.

Capture the runtime/source pin, native cwd, actual Hook input shape, dispatch and terminal
events, stored handoff/observation identities, the wait/integration trace, and any targeted
spot-check. Report observed model behavior, evidence association, product judgment and
remaining UNKNOWN separately. Tests, Reviewer READY, native Completed and mechanical
DONE are distinct observations; none supplies the Controller's product judgment.
